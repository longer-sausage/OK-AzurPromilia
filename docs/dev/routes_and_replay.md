# 一条龙顺序、导航路线与轮椅方案（批次 D）

三块都是「把固定流程复用起来」的工具，共同点是**数据是 JSON、执行走任务体系**：

| 功能 | 数据位置 | 执行入口 |
|------|----------|----------|
| 一条龙顺序 | `configs/DailyTask.json` 的 `任务顺序` | 「一键日常」任务 |
| 导航路线 | `configs/routes/<名字>.json` | 「导航路线」任务 |
| 轮椅方案 | `configs/schemes/<名字>.json`，可导出成流程 | 「流程 / 队列」任务（跑导出的流程） |

## 1. 一条龙顺序

### 配置项

`一键日常` 新增 `任务顺序`（逗号分隔，`，`/`、`/`;` 也认）：

```text
家园每日,委托每日,每日收菜
```

排序规则（`src/tasks/daily/order.py`）：

- 只认已知任务名，**未知项忽略**（换版本删任务不会崩）；
- 配了但漏掉的任务**追加在末尾**并保持原有相对顺序 —— 新增任务不会因为老用户的
  顺序串里没有它就被静默跳过；
- 空串退回代码里的默认顺序。

默认顺序仍是「家园 → 委托 → 收菜」：委托战斗会推进日常/周常活跃与大月卡进度，
收菜殿后能把战斗产生的进度一并领走。

### 「一条龙顺序」页

`src/gui/daily_order_tab.py`：

- 列表**可拖动排序**（`QListWidget` 的 InternalMove；框架本身没有任何 drag&drop 控件）；
- 勾选框控制该项是否执行（写回对应开关键）；
- 「上移 / 下移 / 恢复默认 / 刷新 / 保存顺序与开关」；
- 保存时若任务正在运行会拒绝写入，避免和运行中的编排抢配置。

### 每项自己的参数

一条龙的每一项其实都是**独立注册的任务**（`家园每日` / `委托每日` / `每日收菜`），
参数存在各自的 `configs/<任务名>.json` 里，归属权、多账户覆盖、配置迁移都由那个任务自己管。
我们**不去复制这份配置**（复制必然漂移），只做摘要 + 跳转：

- 选中一项，下方显示它**与默认值不同**的参数，例如
  `委托每日（有独立配置文件）：每日委托=金币本，战斗次数=3`；
- 「打开配置文件」直接用系统默认程序打开 `configs/委托每日.json`（不存在就先建一个 `{}`）；
- 「刷新参数」重读；任务运行中也只是读，不会写。

核心逻辑在 `src/core/task_config_summary.py`（纯函数，可离线测试）：
`summarize_config` 跳过 `_` 开头的隐藏键、跳过与默认值相同的键、布尔转「开/关」、
列表用「、」连接、超长值截断到 24 字，**最多 4 项**（够看就好，不糊满屏）。

### 跑完之后的「执行情况汇总」

`src/tasks/daily/daily_summary.py` 把 `DailyTaskRunner.final_summary` 渲染成文本行
（进日志），并写一份 txt 报告到 `<临时目录>/<软件名>/<任务名>/<任务名>_<时间戳>.txt`：

- 状态共 5 种：`未开始` / `运行中` / `完成` / `部分失败` / `异常结束`，都走 `_tr()` 翻译；
- 多轮循环会按「第 N 轮（账号: 某人）」分段，单账户单轮则省略表头（避免噪音）；
- 失败明细按账号分组（`id:42` 兜底），空消息显示「未设置失败消息」；
- 同一秒内连续生成**不会互相覆盖**（`open("x")` + 序号后缀）；
- 超过 `keep_days`（默认 7 天）的旧报告在下次生成时清掉。

⚠️ 这几处文案用的是 `_tr()` 局部变量（不是 `obj.tr()`），所以静态 i18n 检查以前扫不到，
漏翻了 19 条；现在 `tests/test_imports.py` 同时扫 `tr(` 与 `_tr(` 字面量，
并额外检查 `final_summary["status"]` 的中文状态词在 6 个语种里都有译文。

## 2. 导航路线

### 数据

```json
{
  "name": "每日委托路线",
  "description": "从主界面到委托面板",
  "waypoints": [
    {"page": "page_main"},
    {"template": "commission_icon", "timeout": 10},
    {"click": [0.5, 0.5], "wait": 1.0}
  ]
}
```

一个航点可以同时有多个动作，执行顺序固定为：**页面 → 等模板 → 点击 → 等待**。

| 字段 | 说明 |
|------|------|
| `page` | 目标界面名；走 `ui_ensure` 的 Page 拓扑导航，到不了算失败 |
| `template` | 等某个模板出现（超时算失败） |
| `click` | 比例坐标 `[x, y]`（0..1） |
| `wait` | 该航点做完后再等几秒 |
| `timeout` | 该航点的超时，默认 30s（页面导航与等模板共用） |
| `note` | 备注，不影响执行 |

校验（`Route.validate()`）会拒绝：空路线、空航点、`timeout <= 0`、比例坐标越界，
以及（如果传了已知界面集合）未注册的界面名。

### 执行

「导航路线」任务（`src/tasks/onetime/route_task.py`，`support_schedule_task=True`）：

- 配置 `路线文件`（`configs/routes` 下的名字）+ `从断点继续`；
- 断点**按整条航点**记录，复用流程那套 `CheckpointStore`（key 是 `route_<名字>`），
  跑通后自动清断点；
- **路线改过就忽略旧断点**：断点里存了航点结构的摘要（fingerprint），改了航点后
  `resume` 会从头跑，而不是「跳过前 N 个」跳到错误的航点上。流程也是同一套规则，
  只改名字/说明不会让断点失效（只看步骤结构）；
- 失败会调用 `mark_task_failure`（顺带存失败帧，可在「工具与诊断」里复测）。

## 3. 轮椅方案

「轮椅」= 重复度极高的固定操作。方案不需要新引擎：**录制段就是流程步骤**，
方案只是把若干段拼起来，再交给 `FlowExecutor` 跑。

```json
{
  "name": "深渊轮椅",
  "loop": 2,
  "between_wait": 0.5,
  "segments": [
    {"label": "进场", "events": [ ... 录制事件 ... ]},
    {"label": "输出循环", "steps": [{"type": "key", "key": "e", "duration": 0.2}]}
  ]
}
```

拼接规则（`src/core/replay.py`）：

- 每段优先用 `steps`（已经是流程步骤时），否则用 `events` 走
  `convert_recording()` 转换；
- 段与段之间插入 `between_wait` 秒的 `wait`（默认 0.5，0 表示不留缝）；
- `loop > 1` 时整串包进一个 `loop` 步骤（受流程 1000 次上限约束，`0` 会被拒绝）；
- 每段转换跳过的输入（右键/滚轮等）汇总进 `SchemeReport`，**如实报告**而不是忽略；
- 拼出来的流程同样过 `validate_flow`（500 步 / 4 层），超了直接报错而不是硬跑。

导出：`scheme_to_flow_file(scheme)` 把方案写成 `configs/flows/<名字>.json`，
之后就能在「流程 / 队列」任务或队列里跑。

## 4. 实时辅助（通用战斗辅助）

`src/tasks/trigger/auto_combat_assist_task.py`（「实时辅助」）。

和其它触发任务不同，它**不针对某个玩法**：只按你配置的键和节奏持续操作，
所以不依赖任何游戏内界面模板就能用。可选「前置模板」把它限定在特定场合。

| 配置项 | 默认 | 说明 |
|--------|------|------|
| `按键序列` | `q,e,r` | 逗号分隔（`，`/`;`/`|`/空格都认），按顺序**轮转**；相邻重复自动去掉 |
| `动作间隔(秒)` | 0.8 | 两次 run 之间的最小间隔（冷却），靠它限流而不是靠 `trigger_interval` |
| `前置模板` | 空 | 可选模板名；不填表示不禁用，填了就只在它出现时动作 |
| `最大连续次数` | 3 | 单次 run 最多按几次，避免一个任务长期占住触发轮转 |
| `记录日志` | False | 每次动作写一行日志，方便核对节奏 |
| `_按下时长(秒)` | 0.05 | 按键按住时长（`_` 前缀 = UI 不显示） |

设计要点：

- `trigger_interval = 0` 表示每轮都参与调度，**靠自己的冷却限流**；
- 识图失败或没有配置序列时返回 `False`，不抛异常（触发任务不该把框架拖崩）；
- 停用再启用时调 `reset_state()` 从头开始轮转。
